# Analysis Improvements — Phase 2.1

## Background

A user asked "what is the best move?" in a position where the side-to-move's queen was attacked. The model called `analyze_position`, received six top PV lines, and replied based on the top line — without recognizing that every reasonable defense still lost the queen. Only after a follow-up question ("does the queen have anywhere safe to go?") did the model enumerate queen moves manually (`make_move` → `analyze_position` → `undo_move` per square) and conclude the queen is lost.

Root cause: `analyze_position` returns engine best-play PV(s). When a piece is forced lost, those lines all converge on "best surviving line still loses the piece," and the model can read that as "best move has a bad eval" rather than "this piece is lost in every defense." The MCP server has no primitive for "evaluate this specific set of candidate moves," so answering "is there ANY queen escape" requires N model-driven round-trips.

This phase pairs the smallest server change that adds the missing primitive (Phase 2.1 / option #2) with a model-side rule that tells the assistant when to reach for it (Phase 2.1 / option #1).

## Goal

After Phase 2.1, when a major piece is under attack the model should be able to ask Stockfish, in a single round-trip, "what is the best line if I restrict play to this list of moves?" — and should know to do so without being prompted.

## Option #1 — Model-Side Guidance

### Where it lives

Two coordinated places, intentionally redundant so the rule is available whether the user invokes a skill or not:

1. `instructions` string returned from `ServerHandler::get_info` at `src/server.rs:368`. This text is delivered to every MCP client on handshake and is the most reliable channel.
2. A new skill file (working name `chess-analyze`) that elaborates the same rule plus worked examples. The skill is for the human-facing client (Claude Code / Claude Desktop) and can be longer.

### The rule

When answering "what is the best move?" or any evaluative question:

1. Read the top line's `score` and `material_swing.net_for_stm`.
2. If `score.cp <= -200` (or `score.type == "mate"` against side-to-move) **and** the top line's `captures` include a major piece (`Q`, `R`) belonging to side-to-move within the first 3 plies, treat the position as a *suspected forced loss* of that piece. Do not stop at the PV.
3. Identify the threatened piece's square from the current board.
4. List all legal moves of that piece (subset of the board's `legal_moves`).
5. Call `analyze_position` once with `restrict_to_moves` set to that subset (see Option #2). The returned `score` is the best achievable evaluation across all escapes.
6. Report explicitly: "every legal move of the queen leaves the eval at X — the queen is lost," or "Qd2 holds the eval at Y — the queen survives by retreating."

The rule does not fire on minor-piece losses (B, N) by default; those are common and the existing PV explanation is usually adequate. Pawn losses never trigger it.

### Why these thresholds

`-200 cp` is roughly "down a minor piece minus some compensation." A queen-for-bishop loss is `-600 cp` or worse, so the threshold has headroom. The 3-ply window catches "the engine just took the queen" but not deep positional sacrifices the engine prefers. These numbers are starting points; they should be tuned after the rule is in use.

### What to write in the skill

Skill body, roughly:

- One paragraph statement of the rule.
- The exact thresholds and which fields to read.
- A worked example: the queen-loss position from the failed interaction. Show the JSON the model sees, the threshold check, the follow-up `analyze_position` call with `restrict_to_moves`, and the final phrasing.
- A counter-example: a position where the eval is `-300` because of a positional weakness but no major piece is hanging — the rule does not fire and the normal PV answer is correct.

The skill should not duplicate general chess knowledge; it is purely an interpretation protocol for this server's output.

### Where to store the skill

Place under a `skills/` directory in the repo. The exact mechanism for loading skills is a client concern, not part of this MCP server — the file is documentation/instruction that the user can register with their client.

### Risk

Skill guidance is advisory; the model can ignore it. The redundancy between `instructions` (always delivered) and the skill file (only loaded if the user wires it up) mitigates this. The rule will also catch some false positives (e.g., deep queen sacrifice lines where the engine's eval is genuinely positive despite a queen disappearing). The output should still be informative — the model would report "the queen is sacrificed but eval stays at +3" — but it does add round-trips.

## Option #2 — `restrict_to_moves` (searchmoves) on `analyze_position`

### Tool input change

Add one optional field to `AnalyzePositionArgs` in `src/server.rs:60`:

```json
{
  "session_id": "uuid | null",
  "fen": "string | null",
  "depth": 20,
  "multipv": 6,
  "restrict_to_moves": ["d1d2", "d1e1", "d1c1"]
}
```

Semantics:

- When `restrict_to_moves` is omitted or empty, behavior is unchanged.
- When present, Stockfish is told to consider only those moves as the first ply. The returned `lines` are ranked among them.
- Moves must be in UCI format, must be legal in the analyzed position, and must be a subset of the position's legal moves. Otherwise return `invalid_argument` listing the offending move and the position's legal moves (same shape as `make_move`'s illegal-move error).
- `multipv` is silently clamped to `min(multipv, len(restrict_to_moves))`.

### Stockfish wire format

UCI's `go` command accepts a `searchmoves` clause: `go depth 20 searchmoves d1d2 d1e1 d1c1`. This is a single string append in `src/engine.rs` where the `go depth …` line is composed today (around line 117 / the `setoption … MultiPV` block — exact line shifts after edits).

The engine must still apply `setoption name MultiPV value <N>` before `go`, where N is the clamped value.

### Cache interaction

The cache key today is `(normalized_fen, depth, multipv)` — see `src/cache.rs:54`. With `restrict_to_moves`, identical positions analyzed with different restriction sets are different analyses and must not collide.

Two acceptable approaches:

1. Extend `CacheKey` with `restrict_to_moves: Vec<String>` (sorted, deduplicated, lowercased for stable hashing). Restricted analyses sit beside unrestricted ones in the LRU. Recommended.
2. Skip the cache entirely when `restrict_to_moves` is non-empty. Simpler, but loses caching for the repeated-question case (the model may run the same restricted query twice while reasoning).

Pick (1). The sort+dedupe normalization is straightforward.

### Response shape

Unchanged. The existing `lines` array already has `score`, `pv_uci`, `pv_san`, `captures`, `material_swing` per rank. The model reads `lines[0].score` as "best the side-to-move can do given the restriction."

Consider adding a `restricted_to: ["d1d2", "d1e1", "d1c1"]` field on the response so the model can confirm the engine respected the restriction (and so cached responses are self-describing).

### Progress and cancellation

Unchanged. The `engine_started` / `depth_complete` / `completed` events still apply.

### Engine timeout

Restricted searches at fixed depth are usually faster than unrestricted searches at the same depth (smaller root branching). The existing `ENGINE_TIMEOUT` (5 minutes, `src/engine.rs:20`) is fine.

### Spec doc update

Update `design/mcp_specs.md` `analyze_position` section to document the new field, the validation rules, and the cache-key extension.

### Tests

Unit tests:

- `restrict_to_moves` containing an illegal move returns `invalid_argument` with the offending move surfaced.
- `restrict_to_moves` with one move returns exactly one ranked line whose first PV move is that move.
- `restrict_to_moves` does not collide in the cache with the unrestricted query at the same depth/multipv.
- `multipv` larger than `restrict_to_moves.len()` is silently clamped.
- Sorting/dedup is order-independent: `["a", "b"]` and `["b", "a", "a"]` produce the same cache key.

Integration test (ignored by default, behind real Stockfish):

- A queen-attacked position; pass all queen moves as `restrict_to_moves`; assert all returned line scores are within a "losing" band; assert the move with the highest score is the one a human would expect.

## Sequencing

Implement #2 first — without the primitive, #1 has nothing to call. Then write the skill and update the `instructions` string. Run the failed-interaction position end-to-end as a manual smoke test before closing the phase.

## What is intentionally not in this phase

- No new tools. `evaluate_moves` (tabular eval-per-move output), static SEE-based hanging-piece detection, and cross-line motif extraction are all in `202605_improve_2_2.md`.
- No change to `multipv` defaults.
- No change to cache capacity or eviction policy.
