# Analysis Improvements — Phase 2.2

## Background

Phase 2.1 (`202605_improve_2_1.md`) gives the model a way to ask "what is the best line if I restrict the first move to this set?" plus a rule for when to ask. That covers the immediate failure case: queen attacked, no escape, model doesn't realize the queen is forced lost.

Phase 2.2 collects three deeper improvements that go beyond restricted search. Each addresses a different shortcoming of "PV-only" output. They are independent; each can ship alone, and the order below is the order I'd consider implementing them.

## Option #3 — `evaluate_moves` Tool

### Motivation

`restrict_to_moves` (Phase 2.1) tells the model "the best of these moves keeps the eval at X." That answers "is there any escape." It does not answer "how much worse is each candidate than the others." For a question like "should the queen retreat to d2 or e1?", the model needs an eval *per move*, not the best across the set.

The model can simulate this today with N `make_move` + `analyze_position` + `undo_move` round-trips. That's slow, easy to get wrong (forgetting an undo), and pollutes the session history with rolled-back moves. A dedicated tool is cleaner.

### Tool shape

New MCP tool, name `evaluate_moves`:

```json
{
  "session_id": "uuid | null",
  "fen": "string | null",
  "moves": ["d1d2", "d1e1", "d1c1"],
  "depth": 14
}
```

Rules:

- Exactly one of `session_id` or `fen` (same as `analyze_position`).
- `moves` is required, non-empty. Each move must be legal in the analyzed position. Same `invalid_argument` shape as `make_move` on an illegal entry.
- `depth` is optional; default lower than `analyze_position` (suggest 14 vs. 20) since N searches multiply runtime. The exact default should be tuned during implementation.
- No `multipv`. Each candidate is searched at `multipv=1` to keep total time bounded.

Response:

```json
{
  "schema_version": "1.0",
  "fen": "string",
  "depth": 14,
  "results": [
    {
      "move": "d1d2",
      "score": { "type": "cp", "cp": -780, "mate_in": null },
      "pv_uci": ["d1d2", "..."],
      "pv_san": ["Qd2", "..."],
      "material_swing": { "...": "..." }
    },
    { "move": "d1e1", "...": "..." }
  ]
}
```

`results` is sorted by score, best for side-to-move first. The first entry's score equals what a `restrict_to_moves` analysis would return — the tools agree on the boundary case.

### Implementation

Two reasonable approaches:

1. **N sequential `analyze_position` calls under the hood**, each with `restrict_to_moves: [single_move]` and `multipv=1`. Simplest; reuses Phase 2.1 plumbing entirely. Each call is independently cacheable. Total time ≈ N × per-search time.
2. **One Stockfish search with full multipv, then map results back to the requested moves**, falling back to per-move searches for any moves not in the top multipv. Fewer engine restarts, but the logic for "did Stockfish rank this move?" is fiddly and the win is small at typical N (≤ 8).

Pick (1). It is roughly N times slower than a single `analyze_position`, but N is small (the model will pass legal moves of one piece, typically 4–8), and caching means a follow-up question reuses prior results.

### Cache interaction

Per-move results sit in the existing `analyze_position` cache by reusing `restrict_to_moves: [single_move]` cache keys. No new cache structure.

### Progress

Emit a `move_evaluated` progress event per completed candidate so the client can show partial results. Final `completed` when all are done.

### Cancellation

If cancelled mid-batch, return the partial `results` already computed plus the `analysis_cancelled` error code. Partial results are still useful to the model. Match the existing cancellation semantics — partial searches are not cached.

### Tests

- N searches in the response, sorted by score.
- Illegal move in `moves` rejected up front; no search runs.
- Cancellation mid-batch returns partial `results` and a structured error.
- Cache hit on second call with the same `moves` set.

## Option #4 — Static Hanging-Piece Detection (SEE)

### Motivation

Even without running Stockfish, "the queen is on a square attacked by a pawn and defended by nothing" is decidable from the position alone in microseconds. A static exchange evaluator (SEE) is the standard tool: for each piece of side-to-move, it computes the material result if the opponent plays the best capturing sequence on that square. A negative SEE means the piece is hanging.

If the `analyze_position` response surfaces this directly, the model sees "your queen on d4 has SEE = -8" without needing any rule, threshold, or follow-up call.

SEE has limitations: it does not see absolute pins (a piece defended by another piece that is itself pinned will look defended when it isn't), overloaded defenders, or back-rank/X-ray effects. Those cases still fall back to engine search. But the common case — "you just left a piece en prise" — is exactly what SEE solves cleanly.

### Response shape

Add a `threats` field to `AnalysisResult` (`src/cache.rs:44`):

```json
{
  "threats": [
    {
      "square": "d4",
      "piece": "Q",
      "side": "black",
      "attackers": [
        { "square": "e3", "piece": "P" },
        { "square": "h4", "piece": "Q" }
      ],
      "defenders": [],
      "see": -9
    }
  ]
}
```

Include only entries with negative SEE for the side to move. Empty array if nothing is hanging.

Computed once per position, not per line. Independent of `depth` / `multipv`. Should not be part of the cache key — it is a pure function of FEN.

### Where it goes

A new module `src/threats.rs` (or extend `src/pv_explain.rs`). `shakmaty` (already a dependency) provides attack-table generation and piece location, which is most of what a SEE implementation needs. A SEE implementation in Rust is ~100 lines.

### Caching

The `threats` array is a function of the normalized FEN. Cache it in a separate small map keyed by `normalized_fen`, or recompute on every call — it is cheap enough (sub-millisecond) that recomputation is acceptable for a first version.

### Tests

- Starting position: empty `threats`.
- A queen-attacked-by-pawn position: one entry, SEE = `-9`.
- Defended queen (queen attacked by pawn, defended by rook): no entry (SEE positive).
- Multiple hanging pieces: all surfaced.
- Side-to-move discrimination: a piece hanging for the side *not* to move is not in `threats`.

### Risk

If SEE is added to a response field that the model may read instead of Stockfish's eval, it can mislead in the pin/overload cases mentioned above. The field name (`threats` not `material_loss`) and the documentation ("static evaluation; does not see pins or overloads") should make the limits visible. The engine's eval remains the source of truth.

## Option #5 — Cross-Line Motif Extraction

### Motivation

`analyze_position` already returns `multipv` (default 6) lines, each with its own `captures` and `material_swing`. A pattern hiding in plain sight: if all six top lines have a capture of side-to-move's queen within the first 4 plies, the queen is forced lost regardless of which best-six line you pick. The data is in the response; nothing surfaces the pattern.

This option is pure server-side post-processing: derive a `forced_motifs` field from the existing `lines` and add it to the response. Zero new engine calls.

### Response shape

```json
{
  "forced_motifs": [
    {
      "kind": "piece_loss",
      "piece": "Q",
      "side": "black",
      "lines_count": 6,
      "lines_total": 6,
      "avg_score_cp": -820
    }
  ]
}
```

`lines_count` / `lines_total` shows agreement strength — "5 of 6" is suggestive, "6 of 6" is forced (within the search horizon).

Other motif kinds worth detecting (each in scope or out of scope as the implementer decides; `piece_loss` is the minimum):

- `piece_loss`: same role of side-to-move is captured in N of M top lines within ply ≤ K.
- `forced_recapture`: side-to-move captures a specific piece on the same square in N of M lines.
- `forced_check_sequence`: side-to-move is in check at the same depth in N of M lines.

The first one is the queen-loss case. The others are nice-to-haves.

### Algorithm

For `piece_loss`:

1. For each line, find the first `CaptureEvent` where `captured` is a piece of side-to-move and `side` is the opponent's color, with `ply ≤ K` (K = 4 is a starting threshold; this is "loss in the first two pairs of moves").
2. Group by the captured piece's role.
3. For each role, count how many lines contain such a capture.
4. Emit a `piece_loss` entry when the count is ≥ ⌈M/2⌉ + 1 (strict majority). Always emit when count equals M (forced).

### Where it goes

A new function in `src/pv_explain.rs` consuming `&[AnalysisLine]` and the side-to-move color, returning `Vec<Motif>`. Called from `run_analysis` (`src/server.rs:264`) after engine results come back, before serializing.

### Caching

Motifs are derived from cached lines, so they should be derived on read from the cache, not stored. Otherwise a future schema change to the motif format requires invalidating the entire cache. Recomputation is microseconds.

### Tests

- 6/6 lines lose the queen → one `piece_loss` motif with `lines_count == 6`.
- 3/6 lines lose the queen → no motif emitted (below threshold).
- A position with no captures in any line → empty `forced_motifs`.
- Side-to-move discrimination: opponent's queen captured in every line is not a `piece_loss` for side-to-move.

### Risk

This is the riskiest of the three to interpret naively. "Forced loss in top 6 lines" depends on `multipv=6` actually exploring the right defensive moves. If the engine's top six are all aggressive attempts and the queen-saving retreat is move #7, the motif fires falsely. Mitigation: when the `forced_motifs` confidence is "all N lines agree," it is still possible the saving move was outside multipv. The skill rule from Phase 2.1 (enumerate the piece's legal moves with `restrict_to_moves`) is the verification step; the motif is the hint, not the proof.

## Ordering and Selection

If only one of #3, #4, #5 will be built:

- **#4 (SEE)** is the highest information-per-line-of-code. It catches the failure case statically with no engine cost, and the limitations are well-understood.
- **#3 (`evaluate_moves`)** is the most powerful when the model needs to *explain* between options, not just confirm a loss.
- **#5 (motifs)** is the cheapest in implementation but the easiest to misinterpret. Build it last, after the other primitives are reliable.

If all three ship, they layer naturally: SEE flags the threat statically, `restrict_to_moves` (from Phase 2.1) verifies it forced, `evaluate_moves` ranks the alternatives, motifs summarize patterns the model would otherwise have to spot itself.

## What is intentionally not in this phase

- No change to PV explanation logic (`src/pv_explain.rs`) beyond the additions named above.
- No background analysis or speculative search.
- No change to MCP transport, resources, or the existing tool list aside from the new `evaluate_moves` tool.
